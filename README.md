### Задвоение reasoning_cost — 15.4% всех запросов, системный механизм
Сигнатура: `reasoning_cost` в выгрузке = ровно 2 × эталон, остальные компоненты точны.
- **Подтверждение (оконная модель):** `b92ae97c-7c85-4953-b4ad-086cc0d87e0b` (ООО Милк,
  deepseek-flash, 13.10 00:05:39, off-peak окно t00-01): reasoning 372 токена списан по
  `1.56/1M = 0.00058032` вместо `0.78/1M = 0.00029016` → **+0.00029016**; input/cache/output точны.
- **Подтверждение (flat-модель, окон нет):** `72698c7e-396b-4e80-9413-4fd48c3396f8`
  (ООО Вектор, deepseek-v4-flash, одна цена на сутки): reasoning `2322 × 1.0/1M = 0.002322`
  вместо `2322 × 0.5/1M = 0.001161` → **+0.001161**. Крупнейший: `chatcmpl-9207c55a-…`
  (v4-pro): 0.07827612 vs 0.05352984, **+0.02474628**.
- **Почему один механизм:** на flat-моделях объяснение «не то окно» невозможно — значит,
  компонент именно удваивается; на оконных моделях peak случайно = 2×off-peak, та же сигнатура.
  Разрез по часам: доля 0.08–0.18 равномерно по всем 24 часам, без ночной кластеризации →
  не расписание, а двойное начисление компонента. По моделям: v4-pro-0813 684 (+6.118),
  v4-pro 1129 (+3.015), flash 1341 (+1.039), v4-flash 1065 (+0.395), 0731 463 (+0.285), v3.2 93 (+0.131).

### Тип A: off-peak ставка применена в peak-окне

## 3. Воспроизводимый расчёт и порядок проверок

**Два независимых движка, кросс-валидация:** Python (Decimal, `billing_check.py`) и SQL
(PostgreSQL-запросы, портируемые на SQLite — `sql_demo.py`, [sql_solution.md](sql_solution.md)).
Итоги идентичны до 1e-10; построчная кросс-сверка 6 063 расхождений — **0 несовпадений**
по типам и суммам. В SQL деньги хранятся в целых единицах 1e-10 USD (точная арифметика
без NUMERIC/REAL), день недели и час вычислены при загрузке — запрос один и тот же для обоих движков.

**С каких проверок начал и почему** (легенда — сбой Postgres, поэтому сначала целостность, потом деньги):
1. Структура: дубли request_id (post-failure replay), NULL, границы периода.
2. Инварианты токенов: `cached ≤ prompt`, `text_tokens ≥ 0`, отрицательные значения.
3. Ссылочная целостность: org → прайс, model_group → прайс; правило «модель вне прайса = 0».
4. Внутренняя согласованность выгрузки: `total = Σ 8 компонент` (ловит битые total без эталона).
5. Самопроверка прайса: окна каждой модели покрывают 168 ч без пересечений (проверяю инструмент, не данные).
6. Эталон на flat-моделях (одна цена) — исключает неоднозначность окон; сходится до знака → формулы верны.
7. Оконные модели: join по (прайс, модель, день, `[h_from, h_to)`), расчёт компонент без округлений.
8. Классификация по сигнатурам с **подтверждением пересчётом**: альтернативная ставка должна
   воспроизвести выгрузку компонент до 5e-9, иначе тип не присваивается.

**Точность:** компоненты выгрузки хранятся с полной точностью (9–10 знаков), `total_cost`
округлён до 8 (ROUND_HALF_UP). Компоненты сверяются с неокруглённым эталоном (допуск 5e-9);
округление — только при выводе. Порог значимости 1e-6 обоснован шумом округления total (≤5e-9).

## 4. Причины расхождения и запрашиваемые данные

| Гипотеза | Обоснование из данных | Что запросить |
|---|---|---|
| A: стационарный механизм ~25% в peak-окнах — stale off-peak конфиг на части инстансов / баг-ветка кода / частичный backfill | доля ≈25% равномерна по всем peak-окнам и обоим дням; не единичный временной блок | instance_id/pod + версия прайса на инстансе; разбивка A по call_type/status (проверяемо в текущей выгрузке); created_at/updated_at vs start_time; timeline инцидента; changelog прайсов и деплоев |
| B/C: системное задвоение компонента reasoning (retry/двойная запись/версия формулы) | ×2 на flat-моделях исключает оконное объяснение; равномерно по 24 часам; 15.4% строк | changelog кода тарификации, миграции поля reasoning, логи retry, unique-констрейнт по request_id |
| Структурные: порча записей при восстановлении после сбоя | total обнулён при корректных компонентах; часть — с половинными компонентами | логи восстановления/WAL, логи backfill-джобов, какие строки перезаписывались |
| Полнота источников | дублей/пропусков в выгрузке не найдено, но контрольный источник не предоставлен | построчная выгрузка контрольного источника за период; count(*) по часам×org×model из обоих источников |
| Политики округления | total 8 знаков, компоненты 9–10 | precision/rounding mode хранения cost в обоих источниках |

## Нюансы методологии
- **Формула text_tokens:** лист пишет `completion − reasoning − audio − image − video`,
  задание — `− audio_input_tokens − image_tokens − output_image_tokens`. Колонки `video` нет;
  использована формула задания (нормативная). Расхождение — вопрос владельцу данных.
- **Проза vs таблица:** «базовая цена = peak, окна = off-peak» не выполняется буквально
  (0731 t00-01 = peak; ali выходные = peak). Ставки взяты из строк таблицы. Гипотеза
  «единый ночной шаблон» проверена и не подтверждена.
- `cache_creation_cost` и `web_search_cost` взяты из выгрузки по условию задания.

## Ограничения
Выборка «до 4500 строк на пару клиент+модель, равномерно по суткам» **не репрезентативна
для экстраполяции потерь на весь трафик** — она достаточна для обнаружения типов ошибок
и их механики. Масштаб потерь оценивается прогоном по полным логам.
